# Review of RFC-0030 (Missions), 2026-11-26

The operator asked for a review of RFC-0030 by the advisor (Fable 5.1). It was read-only, at main
fb884b2. Each finding is marked VERIFIED (the reviewer read the code path) or SUSPECTED. The
reviewer ran no test, checker, simulator or Mission Control; C1 is read from code paths, not
reproduced with a running gate.

Our note, from checking the reviewer's "not read" list: [RFC-0005](../rfc/RFC-0005-missions.md)
(Proposed, revision 3) is also "Missions": flotilla decides, the simulated duck rehearses every
mission before the real duck, eval-harness measures. RFC-0030 does not cite it. Its auto mode and
RFC-0005's loop overlap (who decides, the sim rehearsal), so RFC-0030 must say how the two relate
before the name `missions` is fixed.

## Verdict: accept with changes

- The cut (planning module, executor, config) is right and matches the code; the decided modes, loop
  and sequencing are sound in shape.
- One critical gap: STOP ends the loop only by assertion. Between steps there is no active run to
  cancel and the gate grants a new lease at once after a STOP, so the next step can start after a
  STOP unless Mission Control latches the mission itself.
- The approval binds to a checksum that omits what decides safety: target (sim or real), the bound
  robot, `sim_first`.
- Approval is a flag (`confirm_required`) and a stage in a diagram, not a server-side state machine
  Mission Control enforces; an MCP client could start plan steps around it.
- The decision record is placed in the wrong store: Mission Control may not write run files, and the
  Decided tab reads a run's `events`. Use the existing event with a `decision`, written by the
  navigator from the `goal_start` spec; no new record kind.

## The plan contract (section 4.2)

- Missing: `target`, a `mission` id, the approval mode, mission budgets, a site snapshot stamp (H2,
  M2).
- `after` with `on_failure: continue`: say that dependents of a failed step are skipped.
- An outcome table: SUCCESS goes to the next step; `refused`, `failed`, `not_found`, `timeout`,
  `stalled`, `stopped_by_guardrail` go to `on_failure`; `cancelled` and `interrupted` end the
  mission `stopped` (H1).
- Partial results: `merge_run_objects` runs during the step (core.py:634), so sightings from a
  failed step are already in the site; say so.
- `sim_first` on a whole plan: with the per-goal rule as built (core.py:532-553: same
  `goals.version`, same site, a twin, 24 h), running the plan on the sim twin first rehearses each
  step, and every replanned step on a real robot is refused until rehearsed. State that as the rule
  for auto on a real robot.
- Multi-robot: `needs.robot: null` with sequential binding lets one mission touch several robots;
  C1's latch covers all of them.
- Step reporting (4.3): `plan-run` needs `reviewing`, `awaiting_approval`, `replanning` states.
  `client` is the token identity (api.py:76-82), not `mission:<id>`; add a `mission_id` column.
