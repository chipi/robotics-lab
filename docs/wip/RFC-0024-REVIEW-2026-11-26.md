# Review of RFC-0024 (one platform) against MVP 2, 2026-11-26

The close-out's third item ([the plan](PHASE5-NEXT-PLAN.md), "Between MVP 1 and MVP 2"): was
bringing Mission Control and the Observatory together right for the long term, with MVP 2 in
mind. The advisor (Fable 5.1) reviewed it read-only at main 54defc1; nothing was run. Each claim
is marked VERIFIED (the code path was read) or SUSPECTED.

**Correction by us:** the review's item 3.5 suspected the adapter `Protocol` was not done. It is:
`RobotAdapter(Protocol)` at `apps/mission-control/src/mission_control/robots.py:278`, with its
contract test, landed in de644db.

## Verdict

RFC-0024 was right, and RFC-0018's one repository was right. Keep both. The costs now visible
are the Observatory's own debt (a monolithic shell, duck-shaped analysis) and the deployment's
co-location assumptions; neither is caused by the one platform, and both become more urgent
because the Observatory is now the front of everything. Not recommended: merging the two
processes (RFC-0024 option A).

## 1. Was one repository and one platform right?

### One repository (RFC-0018)

For:

- The seams are enforced by `check_boundaries.py` (`ALLOWED`, `FORBIDDEN_MODULES`; `EXCEPTIONS`
  and `BASELINE` empty), in `make lint` and CI. VERIFIED.
- The shared libraries change as often as the apps (commits per folder: mission-control 68,
  observatory 59, runfile 48, runner 30, web 15, duck 87). Split, each would be a
  cross-repository release. VERIFIED.
- Both images build from the root and copy `libs/web` and `libs/runfile`; `libs/web` has no
  bundler or release mechanism. VERIFIED.
- The satellites (microduck-nav, robotics-evals) connect by file contract (a golden fixture,
  `result.json` by path) and import nothing of ours, so RFC-0018 §5.1's split trigger has not
  fired; they left for licence, privacy and dependency weight, the right reasons. VERIFIED.

Against:

- One CI `unit` job runs everything on every push; a ROS 2 connector cannot join `ci-fast`.
  VERIFIED shape; future cost SUSPECTED.
- Two URDF parsers: `mission_control/description.py` and `observatory/kinematics.py` produce
  "the same JSON". VERIFIED. The boundary needs a library slot for robot descriptions.
- RFC-0018 §6 step 4 predicted Mission Control "its own repository from birth"; it was built
  as a folder and nothing broke. VERIFIED. The RFC should say so.

### One front (the Observatory's `/control/` proxy)

For:

- The failure-domain split holds in code: the proxy holds no token, decides nothing, reads no
  run, and answers 502 `control_unreachable` when Mission Control is down. VERIFIED.
- `libs/web` is now the larger part of the UI (1,737 lines of JS plus three.js; about 20 modules
  used by each app), enforced by `test_tokens.py`. VERIFIED.
- MVP 2's robots get the body, robot page and inspector from a URDF description. VERIFIED for
  the body path; the Burger's URDF not tried.

Against:

- The proxy's latency on the event stream is unmeasured. VERIFIED unmeasured.
- The Observatory's shell is one 1,872-line `shell.js`; every MVP 2 view change lands in it.
  VERIFIED size.
- With Mission Control on another machine, `OBSERVATORY_CONTROL` would proxy across the tailnet
  with no rule written for that case. SUSPECTED that it bites.

## 2. What should split out, and when

Nothing now.

| What | Trigger |
| --- | --- |
| `libs/runfile` as a published package | A second repository imports it (robotics-evals reading ticks or scans) |
| The ROS 2 connector | First its own folder, image and CI job here; leaves only if the ROS distro drives its release cadence or a second ROS robot appears |
| The Observatory | A second user of its API, or a release pace unlike Mission Control's |
| `libs/web` | Never alone; moves with whichever app leaves |
| Mission planning as an app | RFC-0030 §5's five triggers |
| `apps/nxt-web` | Not planned; MVP 2 step 6 couples it more |
| Flotilla | Deferred; an HTTP contract, no bearing on repository structure |

## 3. What will hurt in MVP 2, ranked

1. The Observatory's analysis and shell are duck-shaped (`anomalies.py` geom names and duck
   kinds; 37 duck/mapd/tof references in `shell.js`), and steps 5a and 8 land there. The
   detectors' `needs` mechanism is the hook to build on.
2. CI shape: one job, no path filters, no ROS image.
3. Co-location baked into deployment and adapters (host network, loopback, a Unix socket, the
   variant picked from the adapter type string).
4. Two URDF parsers; the Burger's upstream description is likely xacro (SUSPECTED).
5. ~~The adapter surface is implicit~~: done in de644db (see the correction above).
6. The unmeasured proxy on the event stream at a ROS robot's rates.

## 4. Recommendations

| # | What | Cost | When |
| --- | --- | --- | --- |
| 1 | Per-project CI jobs with path filters, a job that always runs `check-boundaries`, and a separate ROS connector job with its own image | S to M | Before RFC-0025 step 5a |
| 2 | One robot-description library used by both apps (`libs/robotdesc` or part of `runfile`) | S | With step 2, or before the first non-duck URDF |
| 3 | The Observatory robot-neutral where MVP 2 touches it: detectors declare needs, `ROBOT_KINDS` additive from the run, `shell.js` split by panel before the scan and map panels | M | Step 8 |
| 4 | Measure the proxy on the event stream once; write the rule for a remote `OBSERVATORY_CONTROL` in RFC-0024 §9 | S | Before Mission Control runs on another host |
| 5 | The split-trigger table into RFC-0018; amend its §6 step 4 | S, docs | Now, in the close-out |
